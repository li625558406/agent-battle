# AgentBattle 平台设计文档

日期：2026-09-13
状态：已获用户批准的设计，待实现

## 1. 背景与定位

### 核心洞察

每个用户的 coding agent（Claude Code / Codex / OpenCode / Aider 等）在本地积累私有记忆、skills、CLAUDE.md 配置，导致**同样的模型在不同用户机器上实际解决问题的能力不同**，且差异随时间复利扩大。当前没有任何产品把这个"个体能力分化"作为竞技对象。

### 一句话定位

**本地优先的 agent 养成对战平台**——记忆与 skills 是私有资产（不出域），双人对抗是训练信号与排名依据，能力画像是对局产出物。

### 调研结论（2026-09）

赛道三条路线并存，交叉点无人占位：

1. **Arena 路线**（LMArena/Code Arena、CompassArena）：人类投票 + Elo，云端封闭，评"模型"而非用户的 agent
2. **Benchmark 路线**（SWE-bench、Terminal-Bench、Aider polyglot）：客观判分、本地可跑，但各自刷分，无对抗
3. **对抗路线**（CodeClash、CATArena、DARPA AIxCC、Parallel Code、Qwen Code Arena）：刚起步。CodeClash 执行在云端；Parallel Code/Qwen Arena 是本地单机多开工具，无联网对战、无天梯、无画像

**确认的空白**：无任何项目同时做到「本地执行 + 联网多人对抗 + ELO 天梯 + 多维能力画像 + 配置归因分析」。方法论有学术背书（CATArena arXiv:2510.26852、CodeClash arXiv:2511.00839、Princeton HAL arXiv:2510.11977）。

**风险**：Qwen Code 已把 Arena 收编进官方 CLI，本地对抗正在被大厂工具免费化。壁垒必须建在官方工具不会做的部分：跨场评级累积、能力画像、配置归因分析。

## 2. 产品需求汇总（用户已确认）

| 决策项 | 结论 |
|---|---|
| 定位 | 公开竞技平台 |
| 执行位置 | 用户本地（保住能力分化叙事） |
| 赛制 | 同题竞速/比优 + 攻防对抗 + 盲评投票（三者都要） |
| 能力分析 | ELO 天梯 + 多维画像 + 配置归因 + 对局复盘（全选） |
| 防作弊 | 轻量审计（不做强沙箱） |
| 任务来源 | 官方题库 + 社区共创题库 |
| 交付形态 | 方案 A：开源 Runner + 官方托管平台 |
| Runner 形态 | V1 为 CLI（headless 核心 + 本地 Web Dashboard），桌面壳（Tauri）后置 |

## 3. 总体架构

```
┌─────────────────────────────────────────────────────┐
│              AgentBattle 平台（云端）                 │
│                                                     │
│  Web 前端（天梯/观战/画像/复盘） │ API 网关（REST+WS） │
│  核心服务：匹配 / 对局管理 / 评分引擎 / 题库 /         │
│           审计 / 回放 / LLM judge                    │
│  存储：PostgreSQL（对局/画像）+ Redis（实时状态）      │
│       + 对象存储（事件流/产物 diff）                  │
└──────────────┬──────────────────────────────────────┘
               │ WebSocket / HTTPS（任务下发 ↓ 事件流上传 ↑）
┌──────────────┴──────────────────────────────────────┐
│         AgentBattle Runner（用户本地，开源）           │
│  连接层 / 对局编排 / Agent Adapter 层 /               │
│  隔离层 / 事件采集器 / 判分客户端 / 上传器             │
└─────────────────────────────────────────────────────┘
```

三个关键决策：

1. **Runner 不碰用户 agent 私有文件**：只负责召唤本机已装的 CLI agent 在指定目录执行任务；CLAUDE.md/skills/记忆由 agent 自己加载，Runner 从不读取、不上传内容。隐私是产品承诺。
2. **判分双段式**：客观部分（测试通过）在本地跑平台下发的签名判分包；主观部分（代码质量、盲评）回传产物后在平台侧进行。
3. **能力分析全部在平台侧计算**：基于回传事件流统一口径，保证可比性。

## 4. Runner 设计（V1：CLI）

### 4.1 内部组件

```
agentbattle-runner（headless 守护进程）
├── 连接层：WebSocket 长连接（鉴权/任务接收/心跳/断线重连）
├── 对局编排器：prepare → execute → judge → report 生命周期
├── Agent Adapter 层：
│   ├── ClaudeCodeAdapter  claude -p "<task>" --output-format stream-json
│   ├── CodexAdapter       codex exec --json "<task>"
│   ├── OpenCodeAdapter / AiderAdapter
│   └── 统一契约：detect() / launch(task, cwd, timeout) / parseEvent(line)
├── 隔离层：每局全新临时仓库（git init + 种子仓库 checkout），
│           不用用户真实项目、不用 git worktree（联网模式）
├── 事件采集器：agent stdout → 统一事件流 NDJSON
│   { ts, type: tool_call|file_edit|message|error, tool, args_hash,
│     duration_ms, tokens }
├── 判分客户端：下载签名判分包 → 本地执行测试 → 判分报告（事件 hash 链）
└── 上传器：事件流（NDJSON 压缩）+ 产物 diff + 判分报告 → 对象存储
```

### 4.2 设计要点

- **Adapter 契约**：三方法（detect/launch/parseEvent）。Claude Code 与 Codex 有结构化输出模式，事件解析成本低；Aider 等无结构化输出的降级为只采集文件 diff + 最终结果，画像标注"事件粒度：粗"。
- **对局环境 = 平台下发的全新临时仓库**（种子仓库 + 任务描述 + 测试套件）。同时解决：环境公平、用户隐私、审计干净。用户本地记忆/skills 照常生效（agent 进程在用户环境启动，自己加载）。
- **事件流不含文件内容明文**（只含路径与操作类型）；产物 diff 单独加密上传。
- **超时与中断**：单局平台硬超时；agent 崩溃记 `agent_error`，判技术性失败（Elo 按弃赛，画像单独归因）。
- **UI 形态**：V1 CLI 命令 + `localhost` 本地 Web Dashboard（观战/配置/复盘）。桌面壳（Tauri，非 Electron）在实时观战成为核心体验后再评估。

## 5. 对战流程与赛制

### 5.1 统一流程

发起（用户/系统）→ 匹配 → 双方 Runner 各自拉起 agent → 并行执行（互不可见）→ 判分（客观+主观）→ Elo 结算 → 画像更新 + 复盘报告。

匹配规则：Elo 分段就近 + 任务类型偏好；等待超 60 秒放宽分段；支持直接下战书（对方接受才开打）。

### 5.2 赛制一：同题竞速/比优（V1 主力）

同一任务同时下发双方。判分优先级：

1. 客观测试结果（全过 > 部分过，按通过比例）
2. 都全过 → 平台 LLM judge 按 rubric 打质量分（产物匿名化后同一 judge，分差定胜负）
3. 质量分同分 → 耗时短者胜 → 再同分 → token 少者胜

判分 90% 客观可自动化，是 Elo 天梯的地基。

### 5.3 赛制二：攻防对抗（V2）

防守方限时加固含已知漏洞的种子仓库 → 攻击方在防守产物上找漏洞/埋雷 → 可验证 PoC（flag 机制）客观判定。题目从 CTF-Dojo 类开源题库改造起步。

### 5.4 赛制三：盲评投票（补充判分 + 社区玩法）

对局产物匿名化挂社区投票区，第三方盲选。投票结果作为质量分的众包修正项（对抗 judge 偏差）；投票者按与 judge 结论一致率计权重，防乱投。

## 6. 评分与能力分析体系

### 6.1 ELO 天梯

- 新 agent 1200 分起；前 10 局定级赛 K=40，之后 K=20，高分段高对局量 K=10
- 按任务类型分榜（修 bug/新功能/重构/算法题/调试），支持"总榜第 50、调试榜第 3"的画像叙事
- 季度赛季 + 软重置（向均值收敛 1/3）+ 段位徽章
- 信任分（轻量审计配套）：起点 100，异常信号扣分；低于阈值 → 标记"未验证"，只上待验证榜不上主榜。不做硬封禁，保留申诉通道

### 6.2 六维能力画像（雷达图，0-100，同任务类型内相对分位，近 50 局滑动窗口）

| 维度 | 核心指标 |
|---|---|
| 正确性 | 测试通过率、一次提交通过率 vs 多轮修复 |
| 调试能力 | 报错后恢复成功率、试错→成功收敛速度、盲改比例 |
| 工具效率 | 每任务工具调用数、无效调用率、工具选择合理性（judge 抽评） |
| 成本控制 | token 消耗分位、耗时分位（同题对手归一化） |
| 规划能力 | 前期探索集中度、大范围回滚次数、计划性工具使用 |
| 稳定性 | agent_error 率、卡死检测、跨局方差 |

画像随每局自动更新，可视化 agent 的成长/退化。

### 6.3 配置归因分析（差异化核心功能）

- **A/B 镜像对战**：用户给自己的两个配置（如"带记忆 vs 清空记忆"）发起镜像对战，同任务双份执行，累计 N 局后输出统计结论（如"胜率 +12%，p<0.05，样本 40 局"）
- 只做相关性陈述，不做因果断言
- 隐私红线：平台只统计胜率与事件流指标，**永远不知道配置内容**，界面只显示匿名标签"配置 A vs 配置 B"
- 战略价值：让平台成为 agent 养成训练场——记忆/skills 效果量化是全行业工具空白

### 6.4 对局复盘报告

时间线回放（工具调用序列可视化、可拖动）、关键节点标注（首次报错/大回滚/转折点）、双方行为对比、LLM 生成的自然语言总结。

## 7. 数据流、防作弊与审计

### 7.1 数据生命周期

任务包下发（签名校验）→ 执行中事件流每 5s 增量上传（支撑实时观战 + 留时间线证据）→ 结束后全量事件流 + diff + 判分报告打包上传 → 平台审计流水线 → 评分引擎 → 存储。

### 7.2 轻量审计四道检测网

1. **完整性校验**：判分包平台签名；事件 hash 链（每条事件 hash 含前一条 hash，删改致断裂）；关键段缺失直接标记异常
2. **统计异常检测**：同 agent 历史分布对比（耗时骤降 10 倍、token 归零、通过率突跳 → 人工抽检队列）
3. **产物一致性**：diff 必须可从种子仓库重放应用；平台抽查 10% 对局云端重放判分，与本地结果不符 → 信任分重扣
4. **社区举报**：复盘报告公开（可隐藏 diff 细节），观众可举报异常（如人工改码痕迹）

处罚梯度：标记异常 → 待验证榜 → 该局作废 → 暂停参赛（人工审核）。必须有误报申诉通道。

### 7.3 隐私承诺

| 数据 | 是否上传 |
|---|---|
| 工具调用序列、耗时、token 数 | 是（分析原料） |
| 对局仓库内产物 diff | 是（判分必需） |
| 用户 CLAUDE.md / skills / 记忆内容 | **永不** |
| 对局环境外的任何文件 | **永不** |

`--dry-run` 影子赛模式：先看平台会收到什么数据，再决定联网。透明度即获客话术。

## 8. 错误处理

| 故障点 | 策略 |
|---|---|
| agent 进程崩溃 | agent_error 事件，技术性失败（Elo 弃赛计，画像单独归因） |
| 本地环境缺失 | 任务包声明依赖，Runner 赛前预检，不通过拒接任务不计败局 |
| 断网 | 事件流本地缓冲重连续传；agent 执行不依赖网络 |
| 平台宕机 | 断点保存，恢复续传；超 24h 未上报标记无效 |
| 对手中途退出 | 未完成局不计分；完成方按对手弃赛结算 |
| LLM judge 超时/畸形输出 | 重试 2 次 → 降级纯客观判局；judge 不阻塞 Elo 结算 |

## 9. 测试策略（对抗性优先）

- **判分包校验**：伪造签名、篡改 hash 链、截断/重复上传（幂等）、压缩炸弹
- **Adapter 解析**：非法 JSON、超长行、Unicode 控制字符、ANSI 转义、进程僵死、stdout 刷屏背压
- **评分引擎**：Elo 极端值、对手池为空、赛季边界、并列分
- **异常检测**：构造完美作弊样本验证召回 + 高波动真实样本验证误报率
- **E2E**：mock 平台 + 两个 echo-agent（脚本模拟）跑完整对局闭环回归

## 10. 技术栈

- Runner：Go 单二进制（跨平台、无运行时依赖）；事件 schema 用 JSON Schema，前后端共享
- 平台后端：Go（与 Runner 共享协议库）+ PostgreSQL + Redis + S3 兼容对象存储
- 平台前端：Next.js + WebSocket
- LLM judge：独立服务，prompt + rubric 版本化入库（judge 可复现性是公信力的一部分）
